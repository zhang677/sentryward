Proving a barrier phase without listing schedules

SentryWard runs a kernel once, then proves that no other interleaving could complete an mbarrier phase differently. This page uses a toy kernel to show how it does that: one producer thread loads two tiles with TMA, and one consumer thread waits on the barrier and then reads a tile.


  


  

    
Step 1

    
The happens-before graph

    

      
Each box is an event and each row is the thread that issued it. TMA landings belong to T0 but run asynchronously, so they get their own row and nothing on T0 waits for them. An arrow means "comes first in every schedule".

      
At the start the graph has only program order and issue-to-landing edges. Nothing connects T0 to T1: the consumer's try_wait has no incoming arrow. The phase-boundary check exists to earn that arrow.

The set of events you have run is always an ideal

      
Whenever an event has run, all of its predecessors have run too. A set with that property is called an ideal, or downward-closed set, of the graph. Every partial run is an ideal, and every ideal is a partial run of some schedule. So the question "can any schedule complete phase 0 too early?" becomes "is there an ideal where both counters are zero but some effect on the barrier is missing?" That question is about one set at a time, not about orderings.

    

  


  

    
Step 3

    
One minimization per effect

    

      
First the totals must balance: total arrivals equal the count from mbarrier.init, and the bytes announced by expect_tx equal the bytes landed.

      
Then, for each effect that is not an arrival, the checker asks for the ideal with the fewest bytes outstanding that has every arrival in it and that effect left out. Forcing the arrivals in is safe because, with the totals balanced, missing any arrival keeps the phase open anyway. If the minimum is above zero, no schedule can complete the phase without that effect. If it can reach zero, that ideal is a counterexample.

    

    

    

    

    

      

      

        
How the minimum is found without listing ideals

        
    
          
  • Each effect becomes a node between a source s and a sink t. A landing that removes bytes gets an edge from s with that capacity. An expect_tx that adds bytes gets an edge to t.
    • 
          
  • Each ordering u → v becomes an edge v → u with infinite capacity. If v is on the source side and u is not, the cut would be infinite, so the source side is always an ideal.
    • 
          
  • Arrivals get an infinite edge from s, and the left-out effect gets one to t.
    • 
          
  • After max-flow, the nodes still reachable from s form the minimizing ideal. Its byte count is the cut minus all bytes removed by landings.
    •

Where this lives in the code

      
    
        
  • CheckProperPrefixes and ProperPrefixQuery in cpp/src/analysis/phase_boundary.cpp: one solver call per non-arrival effect, with arrivals in force_in and the effect in force_out. A minimum of 0 or less fails with kPrematurePhaseCompletion, and the ideal becomes the witness.
    • 
        
  • MinimumWeightIdealSolver in cpp/include/sentryward/algorithm/solver/minimum_weight_ideal.h, built on the Dinic max-flow in solver/dinic.h.
    • 
        
  • AddCompletedPhase in cpp/src/analysis/happens_before_graph.cpp adds the completion event. It is kUrgentDerived and has no actor.
    • 
        
  • MemoryRaceChecker flags overlapping accesses (at least one a write) that the final graph leaves unordered.
    • 
      

    

    

      
What this page simplifies

      
    
        
  • SentryWard lowers most instructions to an issue event and a done event. Each pair is drawn as one box here.
    • 
        
  • The solver runs on the graph projected onto the phase's effects. The other events are drawn only to show where the effects come from.
    • 
        
  • The real check also rejects prefixes where the byte count goes negative, and it handles phases with arrival increments.
    • 
        
  • There is only one phase here. Later phases are checked against a graph that already contains earlier completion edges.
    • 
        
  • The wait-freshness and barrier-lifecycle checks (wait_checker.cpp, lifecycle_checker.cpp) are not shown.
